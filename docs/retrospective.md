# Project Retrospective

## What Went Well

One thing that went well was choosing a clear website concept. Caelus Air worked well as a fictional brand because it gave the project a specific identity, audience, and purpose. This made it easier to write the homepage content, choose featured destinations, and explain the brand on the About page.

The two-page structure also helped keep the project focused. Instead of trying to build too many pages or features, I was able to concentrate on meeting the assignment requirements: a homepage, a second page, a shared stylesheet, project documentation, and a professional repository structure.

The project scope statement was helpful because it defined what the project would include and what it would not include. Listing exclusions, such as no real booking system and no live flight data, made the project more realistic and manageable.

## What Went Wrong

One challenge was balancing the technical website work with the project management documentation. It was easier to start the HTML pages first, but the documentation also needed attention because it explains the purpose and process behind the project.

Another challenge was making the project feel like one complete package instead of separate files. The website, README, scope statement, plan, and retrospective all needed to connect to the same project goal. Without that connection, the repository would not feel as professional or organized.

Time management was also a risk. Since the final project required multiple deliverables, waiting too long on any one part could affect the quality of the whole submission.

## What I Would Do Differently

If I did this project again, I would create the README and documentation earlier in the process instead of leaving them for the end. This would make the repository feel more organized from the beginning and would help guide the website content.

I would also spend more time sketching the website layout before writing the HTML. A simple wireframe would help me make faster design decisions and avoid needing to revise the structure later.

For a future version of this project, I would consider adding more visual assets, such as destination images or a logo, while still keeping the site simple and easy to maintain. I would also deploy the website earlier so there would be more time to test the live version before submission.

## Main Takeaway

This project showed me that a successful website project is not only about writing code. It also requires planning, defining the scope, thinking about risks, organizing files clearly, and reflecting on the process. Acting as the unofficial project manager helped me understand how planning and technical work support each other.
