# PROJECT RETROSPECTIVE

**Project:** Caelus Air — Official Website  
**Project Manager:** Ayse Olgundeney  
**Completion Date:** May 2026  

---

## What Went Well

**The planning process paid off.** Writing the scope statement before touching any code forced me to think carefully about what the site needed to be before worrying about how it would look. When I sat down to write the HTML, I already knew exactly what sections were needed on each page, which made the writing process much faster.

**The visual design came together cohesively.** Committing to a single color palette and two fonts from the beginning meant I never second-guessed design decisions midway. The dark, editorial aesthetic fit the Caelus Air brand idea well, and the single external stylesheet kept both pages feeling unified without any extra effort.

**The Work Breakdown Structure kept me on track.** Breaking the project into numbered tasks with due dates made the 12-day timeline feel manageable rather than overwhelming. I could see my progress clearly, which reduced the urge to procrastinate.

---

## What Went Wrong

**I introduced a CSS bug early on.** During the first round of styling, I accidentally set the navigation link color to a dark value that was nearly invisible against the dark background. This slipped by my initial review because I was focused on the layout rather than the details. I caught it only when I opened the site in a fresh browser window and noticed the links couldn't be found.

**Estimating time for the CSS was harder than expected.** I underestimated how long it would take to fine-tune spacing, typography, and responsive behavior. The visual polish pass took longer than the task schedule predicted. In future projects, I would add a buffer specifically for design iteration.

---

## What I Would Do Differently

**Build in a dedicated testing day.** My current plan had testing woven into the development tasks, but in practice, it happened at the end in a rush. A dedicated review day — to test both pages on different screen sizes and browsers — would have given me more confidence before submission.

**Start GitHub Pages deployment earlier.** I set up the live site near the end of the project. If deployment had failed, I would have had very little time to troubleshoot. In future projects, I would deploy an empty placeholder on Day 1 and update it throughout, so the live link is always working.

**Write the retrospective in real time.** I found myself trying to remember details about early decisions by the time I sat down to write this document. In future projects, I would keep a short project journal — even just a few bullet points per session — so the retrospective can be written with sharper detail and more honest reflection.

---

## Final Reflection

This project was a useful exercise in treating a small creative task as a real managed project. The TAME risk analysis, in particular, felt almost theoretical before I started — but the nav color bug and the CSS time underestimate were exactly the kinds of risks it was designed to surface. The biggest lesson: a little planning at the front of a project saves a lot of confusion in the middle.
